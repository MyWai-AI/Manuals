title: "IoTHub"
---

The **IoTHub** page shows the live status of the message path between [Edge devices](/3.2/configuration/edges) and the MYWAI platform. It reports how much traffic is flowing in each direction, how long messages take, and whether any messages are waiting or have failed.

Open it from **Configuration → IoTHub**. Access requires the **View System Status** permission.

The page title is **IoTHub status**. The header shows when the values were last updated. Turn on **Live refresh** to reload the page every 30 seconds; a green **Live** indicator confirms that automatic refresh is active. **Refresh** reloads the values immediately.

<Info>
Rates and delays cover the last 60 seconds. **msg/s** means messages per second. **Waiting** is the number of messages held in a buffer right now. A waiting count of **0** is normal while traffic is flowing.
</Info>

The **Overall** status is computed only from the buffers and steps on this page. The connection status of each Edge device remains on the [Edges](/3.2/configuration/edges) page.

## Overall status

The **Overall** card summarizes the message buffers and the IoTHub steps.

| Status    | Meaning                                                                 |
| --------- | ----------------------------------------------------------------------- |
| Healthy   | Buffers are within the normal range and every step looks healthy.      |
| Degraded  | At least one buffer or step needs attention.                            |
| Outage    | A step is stopped, failed, or critical.                                 |
| Unknown   | No buffer or step metrics are available yet.                            |

When the status is **Healthy** and nothing needs attention, the card states that buffers are empty and all steps look healthy.

Click **Why?** to list the reasons for a status other than Healthy. Each reason names the place to inspect: **Message buffers**, **IoTHub steps**, or a slow segment under **Delay**.

## Traffic

Two cards show the current traffic:

* **Edge → Platform** — messages received from Edge devices, in msg/s.
* **Platform → Edge** — messages sent toward Edge devices, in msg/s.

## Delay

**Delay (slowest step)** shows the slowest segment in each direction:

* **Up** — the slowest segment on the path from the Edge to the platform.
* **Down** — the slowest segment on the path from the platform to the Edge.

If no samples are available yet, the card shows **No delay data yet**.

| Segment            | Direction        | Meaning                                                          |
| ------------------ | ---------------- | ---------------------------------------------------------------- |
| MQTT → buffer      | Edge → Platform  | Time to accept the MQTT message and place it in the buffer.      |
| Buffer → database  | Edge → Platform  | Time to take the message from the buffer and save it.            |
| Platform → buffer  | Platform → Edge  | Time to place a command in the buffer.                           |
| Buffer → Edge      | Platform → Edge  | Time to send the command to the Edge over MQTT.                 |

A segment is reported as slow when its average delay is at least **1000 ms**. **Why?** then names that segment.

## Message buffers

Expand **Message buffers** to see how many messages are held right now. The section header shows **OK**, or an orange chip with the number of buffers that need attention.

| Buffer                         | What it counts                                              |
| ------------------------------ | ----------------------------------------------------------- |
| Edge → Platform buffer         | Messages waiting to be saved on the platform.               |
| Platform → Edge buffer         | Commands waiting to be sent to an Edge.                     |
| Failed (Edge → Platform)       | Messages from the Edge that could not be processed.         |
| Failed (Platform → Edge)       | Commands that could not be delivered to an Edge.            |

A buffer needs attention when:

* a **waiting** buffer holds more than **10** messages, or
* a **failed** buffer holds any message (a count greater than **0**).

Those cards are highlighted. If metrics are not available yet, the panel shows **Waiting for buffer metrics…**.

<Warning>
A failed count that stays above 0 means messages were not processed. Open **Why?** and check the IoTHub ingestion and bridge logs.
</Warning>

A waiting count that keeps growing between refreshes means messages are arriving faster than they are processed.

## IoTHub steps

Expand **IoTHub steps** to see throughput and delay for each step. Use the toggle to switch direction:

* **Edge → Platform**
* **Platform → Edge**

**Edge → Platform** steps, in order:

1. **Receive (MQTT)** — the platform receives the message from the Edge.
2. **Forward to buffer** — the message is placed in the Edge → Platform buffer.
3. **Save to database** — the message is written to the platform database.

**Platform → Edge** steps, in order:

1. **Read command buffer** — a command is taken from the Platform → Edge buffer.
2. **Send to Edge (MQTT)** — the command is published to the Edge.

Each step card shows:

* a state chip: **Healthy**, **Slowdowns**, **Degraded**, **Outage**, or **Unknown** (any other state is shown with the name reported by the service)
* **Throughput**, in msg/s
* **Delay**, in milliseconds
* an error line when the step reports an error rate or a last error

A card is highlighted when the step is not healthy, reports errors, or its average delay is above **500 ms**. A highlighted card with a delay between 500 ms and 1000 ms does not by itself change **Overall** to **Degraded**. **Overall** becomes **Degraded** for delay only when the slowest segment of a direction stays at or above **1000 ms**.

If the selected direction has no metrics, the panel shows **No step metrics for this direction.**

## Reading a problem

1. Check **Overall**. If it is not **Healthy**, open **Why?**.
2. Open **Message buffers**. A growing **waiting** count means the path is falling behind. A **failed** count above 0 means messages were rejected.
3. Open **IoTHub steps** for the direction named in **Why?** and compare throughput and delay across the steps. The highlighted card is the step that needs attention.
4. Use **Delay (slowest step)** to see which segment is the slowest.

If the page cannot load the status, it shows an error. **Session expired. Please sign in again.** means the session is no longer valid. **Unable to load** means the status service did not respond.
